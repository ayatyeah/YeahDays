# Миграции и восстановление

`20261101000000_baseline` фиксирует схему до изменений синхронизации.
`20261101010000_sync_jobs` добавляет версии снимков, триггер и статусы заданий.
Новая база: `npm run db:deploy`. Повторный deploy не применяет миграции заново.
Не использовать `db push` как процедуру выпуска.

## Уже существующая база

1. Сделать `pg_dump --format=custom --no-owner` в защищённое хранилище.
2. Восстановить dump в отдельную базу, проверить приложение и данные.
3. Сравнить старую схему с baseline. Если есть расхождения, сначала сверить
   исторические `docs/sql`, исправить расхождения отдельной миграцией.
4. Только для совпадающей существующей схемы отметить baseline:
   `npx prisma migrate resolve --applied 20261101000000_baseline`.
5. Выполнить `npm run db:deploy`, затем выпустить API и клиент вместе.

Не выполнять baseline CREATE TABLE поверх существующих таблиц. Не отмечать
baseline применённым без проверки схемы. В production эти команды выполняются
оператором с выбранной базой, а не автоматически из локального `.env`.

## Автоматическая репетиция

```bash
DATABASE_URL='postgresql://localhost/postgres' npm run db:restore-check
```

Скрипт допускает только локальный PostgreSQL, создаёт две уникальные временные
базы, применяет миграции, записывает синтетическую задачу, делает dump/restore,
сравнивает отпечатки данных и проверяет работу триггера версий. Затем удаляет
только созданные им базы и dump. Нужны psql, pg_dump, pg_restore, createdb,
dropdb и право создавать тестовые базы. В CI используется service PostgreSQL.

Это проверка механизма, а не подтверждение наличия или пригодности боевых
резервных копий. Для реального backup: отдельное защищённое хранилище,
документированный срок хранения, регулярная репетиция восстановления копии
в изолированной среде. Не хранить dump или пароли в репозитории/логах.

Новые изменения: `prisma migrate dev --name <name>` только на локальной
базе разработчика. Проверить SQL, повторный deploy и restore-check в PR.
