# Память приложения

Production запускается через `railway.json`: Node с `--optimize-for-size`,
кучей V8 до 256 МиБ, young-generation semi-space 2 МиБ и `MALLOC_ARENA_MAX=2`.
256 МиБ — предел old-generation V8, а не всего RSS контейнера: нативные
библиотеки, буферы, код и кэши расходуют память отдельно.

Ограничения приложения:

- Prisma singleton общий для route bundles и instrumentation, включая production.
  По умолчанию пул содержит максимум 5 соединений. Явный `connection_limit`
  в DATABASE_URL сохраняется и имеет приоритет.
- Кэш Next.js в RAM — 8 МиБ; дисковый кэш продолжает работать.
- Фоновые уведомления и очистка research читают по 25 записей. Курсор по ID
  не зависит от удаления предыдущей порции. Лимит dispatch 300 за прогон сохранён.
- Sharp для пользовательских фото и AI planner не сохраняет кэш операций,
  использует один поток libvips на изображение. Общая очередь допускает одну
  обработку фото за раз и максимум четыре ожидающих запроса, далее HTTP 503
  с Retry-After. Media API ждёт слот до чтения тела, AI planner разделяет тот же
  слот для декодирования. Это ограничивает параллельный расход, не весь RSS.
- Ограничитель запросов хранит максимум 5000 ключей и не записывает отклонённые
  попытки. При заполнении отклоняет новые ключи до освобождения просроченных;
  действующие ограничения входа не вытесняются. Окно теперь отсчитывается от
  принятых попыток, повторный отклонённый запрос не продлевает блокировку.

Это короткий синтетический прогон, не прогноз расхода при любом трафике.

порций уведомлений и очистки проверяется отдельными тестами.

Railway перед изменением: 310.1 МБ среднего / 311.5 МБ максимального
расхода за стабильное окно 07:53–08:00 UTC. Первый час с деплоями не следует
использовать как чистое сравнение. После выпуска сравнивать отдельное окно
нового deployment, включая разогрев и реальные запросы:

```sh
railway metrics -s YeahDays -e production --memory --cpu --since 1h --json
```

Источники настроек: [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting),
[Prisma v6 connection pool](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections/connection-pool),
[Sharp performance](https://sharp.pixelplumbing.com/performance/),
[Sharp cache/concurrency](https://sharp.pixelplumbing.com/api-utility/).
Флаг V8 проверен через `node --v8-options` установленного Node.

## Экономичный режим Railway

С 1 ноября 2026 для YeahDays включён Serverless, `PUSH_SCHEDULER=off` и
`NEXT_TELEMETRY_DISABLED=1`. Минутный запрос к БД мешал бы автоматическому сну.
Внешний `ordinary-push.yml` запускается раз в час: напоминания могут опаздывать,
GitHub не гарантирует точное время. LMS обновляется трижды в день, резервная
копия и очистка research выполняются ежедневно. Уведомления с истёкшим окном
могут быть пропущены; это выбранный владельцем компромисс максимальной экономии.

После смены Serverless или переменных нужен успешный deployment. Проверять
фактический статус SLEEPING через Railway API, не посылая HTTP healthcheck
каждую минуту: такой мониторинг сам будет будить приложение. Открытые вкладки
с синхронизацией, внешние запросы, активные соединения БД тоже мешают сну.
Не понижать лимит памяти ради самой цифры: счёт определяется фактическим
расходом, а слишком низкий лимит лишь вызывает OOM. Базы и диски не удалять.

[Поведение сна Railway](https://docs.railway.com/deployments/serverless).

## Фото и часовая нагрузка

Часовой прогон оптимизации RAM на commit `6e0b594`: 3600.8 с, 5768 запросов,
48 загрузок одноцветных JPEG 12 Мп (по 4 одновременно), 0 ошибок. Пик RSS
275.5 МиБ, среднее за последние 5 минут 273.3 МиБ, p95 GET 23.4 мс.
После первых 25 минут средние пятиминутные окна держались около 272–273 МиБ.
В начальное окно разогрева также попали замеры мобильного baseline.
Один час не доказывает отсутствие утечек при любой длительности и нагрузке.

Отдельный тяжёлый тест: 12 загрузок в трёх группах по 4, JPEG из случайных RGB
пикселей 4000×3000, quality 80, около 7.6 МБ каждый. Четыре аватара и восемь
фото постов; production Node с теми же флагами памяти. До очереди peak RSS
435.1 МиБ, через 30 с после нагрузки 417.3 МиБ. После общей последовательной
обработки: peak 307.6 МиБ, после нагрузки 305.8 МиБ, все ответы HTTP 200.
Снижение пика примерно 29%; параллельные клиенты ждут очередь, отдельные
загрузки в этом тесте занимают до ~3 секунд.

Часовой прогон проверял версию до добавления очереди; её эффект отдельно
проверен тяжёлыми фото и тестами ограничения очереди/освобождения после ошибки.
Артефакты локального запуска: `artifacts/reliability/soak-hour.json`,
`photo-before-gate.json`, `photo-load.json`.
